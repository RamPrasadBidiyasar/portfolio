Case study 06 of 06 · AI agent and tool design

An ops assistant that checks the evidence before it answers.

Finding out why a title was missing meant opening four systems by hand. I built a chat agent on LangChain4j and Gemini that calls read-only tools, shows what it found, and asks first before it touches production.

01

Context and problem

Four places to look for one missing title.

When content was missing, in draft, or stale on the web, an engineer had to check what we stored, what the partner actually sent, the logs, and the metrics, in the right order. That order lived in a few people's heads, and every investigation repeated the same manual steps.

System architecture

Conceptual, not the production topology

03

Request flow

Orange steps run only when a fix is needed
  1. An engineer describes the problem in chat.
  2. The agent decides which lookup to run next, using the question, the chat so far and the tool descriptions.
  3. A tool runs and returns its result as JSON. The agent reads it and either calls another tool or moves on.
  4. Tools read stored content, partner dumps, logs and metrics. Nothing is changed.
  5. When there is enough evidence, the agent streams a report: the cause, the evidence it used and the next step.
  6. If the fix changes production, the agent states what it will do and waits for a yes in chat before calling the tool.
04

Technical implementation

RoleDesigned and built the service
TeamXstream backend, Airtel Digital
UsersBackend and operations engineers
StackJava · Spring Boot · LangChain4j · Gemini on Vertex AI · MongoDB
  • 01One agent, many tools. LangChain4j turns the agent into a Java interface and runs the loop of ask, call a tool, read the result. A tool is an ordinary Java method with a plain-language description, and adding one needs no change to the agent setup.
  • 02A short prompt and on-demand playbooks. The always-on prompt only routes. The step-by-step flow for each kind of problem is a playbook the agent loads as a tool result when the question matches. Every turn stays small, and a new domain is one class and one line to register it.
  • 03Tools that never throw. Each tool returns JSON, and a failure comes back as an error message instead of an exception. The agent marks that step as skipped, says so, and carries on with the rest.
  • 04Streaming and two memories. Answers stream to the browser as they are written, and each tool run shows up as a chip. The model remembers the last 32 messages, including tool results. The full visible conversation is stored separately and is never trimmed. A chat belongs to the user who started it.
  • 05Confirm before changing production. Tools that write to production are described so that the agent has to name the target and ask for a yes in chat first. The same actions are also available from an ops panel that does not use the model.
05

Decisions and trade-offs

Decision 01

Playbooks instead of one long prompt

Detailed flows are loaded only when needed, which keeps cost and noise down.

Trade-off. The model has to pick the right playbook. When two could match, it asks which one instead of guessing.

Decision 02

One agent instead of several

One agent with one memory is simple to reason about and to debug.

Trade-off. A long investigation can push early evidence out of the 32-message window.

Decision 03

Confirmation in the instructions

Fast to build, and enough for an internal tool used by a small team.

Trade-off. It depends on the model following the instruction. A server-side confirmation step would be stricter, and is the next improvement.

06

Failure handling and reliability

If

A tool fails

The agent gets an error message, marks that step as skipped and continues with the other checks.

If

The model stops early

If it calls several tools and then writes almost nothing, a second pass with no tools writes the final report from the same memory.

If

A playbook is requested twice

The second request is refused, so the agent does not reload text it already has and loop.

07

Results and metrics

For some catalog-ingestion issues, time to root cause fell by about 90%: from about 30 minutes of checking partner responses by hand to 2–3 minutes. One chat replaces four manual lookups, every answer shows the tools it used, and anything that changes production waits for a yes.
