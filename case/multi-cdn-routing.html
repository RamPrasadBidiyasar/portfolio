Walkthrough

Hover a step to find it in the diagram
  1. A playback request arrives with its context: geography, user and channel.
  2. The engine reads the routing rules from the MongoDB-backed store.
  3. A filter engine removes ineligible CDNs.
  4. A sort engine orders the rest, and a rule-evaluation engine applies priorities and weights.
  5. The selected CDN serves the stream.
  6. If no rule matches or selection fails, the request falls back to stream options ordered by default weight.
The engineering problem

Every request, the best CDN.

IPTV playback needed each request sent to the best CDN as geography, load and CDN health change, and needed to keep playing when a CDN degrades.

Decisions and trade-offs

DECISION 1

Rules as configuration

Routing rules are stored in MongoDB and evaluated per request over geography, user, channel, priority, weights and CDN health.

Trade-off. A rule engine needs its own testing and change history.

DECISION 2

Filter, then sort

A filter engine removes ineligible CDNs, a sort engine orders the rest, and a rule-evaluation engine applies priorities. Rule storage, access and sync mechanisms keep the rules available to the playback service.

DECISION 3

Always have an answer

If no rule matches or selection fails, the request falls back to stream options ordered by default weight. A priority-CDN override gives operators manual control, and fallback decisions are recorded.

Failure handling and recovery

No rule matches

The request falls back to stream options ordered by default weight.

Selection fails

The same default-weight order is used, so playback still gets a CDN.

Operators need control

A priority-CDN override lets them force a CDN, and each fallback decision is recorded.

Results

Playback for 10M+ active users, with buffering reduced from 1% to 0.07%.
