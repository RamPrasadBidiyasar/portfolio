Case study 04 of 05 · Concurrency and atomic limits

A device limit that concurrent logins cannot slip past.

How IPTV login and playback are tied to a device: a session service on multi-zone Aerospike enforces the device limit with one atomic operation, evicts or rejects when the limit is hit, and a shared SDK lets playback and the Subscription Management Service check the same token.

Walkthrough

Hover a step to find it in the diagram
  1. A set-top box logs in.
  2. The session service adds the device to the user's device list with one atomic Aerospike operation, which returns the new device count.
  3. It saves the session under that user and device, with an opaque token, in multi-zone Aerospike.
  4. Playback and the Subscription Management Service (SMS) validate the token through one shared SDK, at login and during playback.
  5. If the count is over the limit, expired sessions are removed first. Then the oldest device is evicted, or the login is rejected if eviction is switched off.
  6. If one zone has a problem, the other zones keep serving.
The engineering problem

Limit the devices, keep playback tied to them.

IPTV needed to limit how many devices can watch at once and keep playback tied to the device that logged in. Logins from several devices can land at the same moment, and a zone can fail, so the limit could not be a check-then-write that two requests might both pass.

Decisions and trade-offs

DECISION 1

Sessions tied to a device

Each session is a record keyed by user and device, with an opaque token. Login, playback and the Subscription Management Service all call the same service.

DECISION 2

An atomic limit

A second Aerospike set holds a per-user list of device IDs. Adding a device to it is one atomic operation that returns the new count, so concurrent logins each see a different count and none slip past the limit.

Trade-off. Over the limit, the service first removes expired sessions, then evicts the oldest device or rejects the login, depending on a setting.

DECISION 3

Eviction and remote logout

An evicted or remotely logged-out device gets a specific error code on its next check. This is what lets a user log another device out to free a slot.

DECISION 4

Multi-zone storage

Sessions live in multi-zone Aerospike, so the service keeps running if one zone has a problem. Expired sessions are cleaned up inline, and orphaned device entries are healed during reads, so no heavy background job is needed.

DECISION 5

Reusable validation

A shared client SDK lets playback and the Subscription Management Service validate tokens the same way, so there is one place to change the rules.

Failure handling and recovery

A zone has a problem

The other zones keep serving, so sessions stay available.

Saving the session fails

The new device entry is rolled back, so a failed login does not use up a slot.

The set-top-box details call fails

Login still works.

Results

IPTV login and device-level playback in one service: a device limit enforced atomically, eviction and remote logout with clear errors, and storage that tolerates a zone failure.
