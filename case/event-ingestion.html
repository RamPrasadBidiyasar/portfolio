Case study 03 of 05 · Throughput and recovery

An event service that survives peaks and a Kafka outage.

How the event ingestion service handles 80–90K events a second at live-match peaks: a shorter request path, isolated Xstream and IPTV stacks, and a buffered path that keeps events safe while Kafka is down.

The engineering problem

Peaks, and a dependency that can fail.

Playback events arrive in bursts during big live matches, about 80–90K per second. A spike or fault in one product should not take down the other, and events should not be lost if Kafka is unavailable.

Decisions and trade-offs

DECISION 1

Shorter request path

The service, rebuilt on Java 25, sends events straight to Kafka, with the extra queue in front of the producer removed and less logging on the request path. One pod went from about 400 to about 2,500 requests per second, roughly 6x.

DECISION 2

Isolate the products

Xstream and IPTV each have their own event service, Kafka cluster and deployment, so a spike or fault stays inside one product and each scales independently.

DECISION 3

Tier the topics

Critical events and routine watch events use different topics with different retention and replication.

DECISION 4

Buffer when Kafka is down

Events are still accepted, held through Cloud Run and Pub/Sub, and replayed into Kafka by Kafka Connect on recovery.

Trade-off. The buffered path cannot separate critical from routine events. This is documented for the team.

Failure handling and recovery

Kafka is down

Events are still accepted and wait in a Pub/Sub buffer.

A spike on one product

It stays inside that product's own stack. Xstream and IPTV do not affect each other.

Recovery

Kafka Connect replays the buffered events into Kafka, where other services keep reading the same topics.

Results

About 6x per-pod throughput, peak load absorbed without cross-product impact, and events buffered rather than lost during Kafka outages.
