Case study 05 of 05 · Fault isolation and fallback

Keep the home screen open when something behind it breaks.

How the home and layout service stays available: the gateway time-boxes every layout request and serves a prepared page from the CDN when it fails, a fallback retry with a kill switch covers content fetches, and autoscaling is smoothed with CPU boost and gradual warm-up.

Walkthrough

Hover a step to find it in the diagram
  1. A client request reaches the gateway filter (Envoy with Lua), which gives it 1.5 seconds.
  2. The filter forwards it to the layout service, which runs its dependency calls in isolated thread pools.
  3. The service reads the primary content source.
  4. If that fetch fails, it retries against a fallback source. A kill switch can disable this, and a response header marks fallback content.
  5. If the layout service is slower than 1.5 seconds or returns a 5xx, the gateway serves a prepared page from the CDN. A job keeps those pages fresh.
The engineering problem

A home page that depends on things that fail.

The home and layout service can fail through server errors, slow responses or overload, and protection inside a service fails together with the service. In the India vs New Zealand T20I, traffic reached 10–11x normal, far past the 2x planned for, so the protection had to sit outside, at the gateway, and still answer when the service could not.

Decisions and trade-offs

DECISION 1

Time-box at the gateway

A Lua filter on the Envoy gateway gives each layout request 1.5 seconds. Slower than that, or a 5xx, and the gateway serves a prepared page from the CDN. A job rebuilds a prepared page for each client and page and refreshes the CDN cache.

Trade-off. A prepared page is the core experience, not always the exact personalized one.

DECISION 2

Fallback with a kill switch

When the primary content fetch fails, the service retries against a fallback source. A kill switch turns that off, and a response header says when fallback content was served, so operators can see it.

DECISION 3

Smooth autoscaling

New pods get extra CPU at startup and a gradual traffic ramp over five minutes once ready, instead of their full share at once. Observed latency spikes during autoscaling fell from 900–1000 ms to 450–550 ms.

DECISION 4

Faster generation

Personalized page generation went from 30 to 100 TPS, with about 30% lower latency, using Java 21, gRPC, thread-pool tuning and parallel asynchronous calls. A slow dependency stays inside its own pool.

DECISION 5

Adaptive concurrency, in deployment

A fixed limit of 85 requests a second per pod did not protect CPU, because requests cost different amounts. The Envoy adaptive concurrency filter limits work in flight instead, between 8 and 35 requests, adjusted every 500 ms against a baseline response time. Excess requests get a 503, which the gateway turns into a prepared page.

Trade-off. Being deployed, so no results are claimed yet.

Failure handling and recovery

The content fetch fails

A fallback retry runs, with a kill switch and a header that marks fallback content.

The layout service is slow or returns 5xx

After 1.5 seconds the gateway serves a prepared page from the CDN. About 1.5% of requests failed at the match-day peak, and customers saw no error screens.

A downstream call is slow

Isolated thread pools keep it from exhausting the whole service.

Results

On match day traffic hit 10–11x normal against a 2x plan, and customers saw no error screens. Availability is now about 99%, and page generation scales from 30 to 100 TPS.
