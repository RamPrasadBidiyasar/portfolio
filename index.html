Case studies

Five systems, what I decided and why

Each one: the problem, the design choices and their trade-offs, and the measured result. Diagrams are conceptual and generalized; they are not the production topology.

01 · Continue Watching and Watch Info v2

Per-user ordering for watch progress, and a fast read path

Problem. Continue-watching and history serve both the Xstream app and the IPTV app at high volume. One user can watch on several devices and write at the same time, so ordering and consistency mattered, and reads had to stay fast.

  • Serialize writes with Kafka. Watch events are keyed by user ID, so one user's concurrent and multi-device writes arrive in order. A consumer writes them to ScyllaDB. The trade-off is asynchronous persistence, covered by a local fallback.
  • Separate data models per product. Xstream and IPTV have their own continue-watching storage, with table-level compaction tuned for it, and a dual-write migration from the old tables.
  • Cache by bucket. Redis and Aerospike caches are scoped per bucket, with bucket-wise diff-sync merge and LRU eviction in the app.
  • Reactive reads. Watch Info v2 serves continue-watching, history and favourites through one contract on Spring WebFlux and reactive ScyllaDB, with independent loaders so one slow section does not hold up the others. Later extended to live TV and microdrama.

Result. Sync latency down by nearly 70%. Watch-history p99 down 75%, with about 4x throughput per instance.

  • Kafka
  • ScyllaDB
  • Redis
  • Aerospike
  • Spring WebFlux

02 · Multi-CDN routing and failover

Choosing the right CDN for every playback request

Problem. IPTV playback needed each request sent to the best CDN as geography, load and CDN health change, and needed to keep playing when a CDN degrades.

  • Rules as configuration. Routing rules are stored in MongoDB and evaluated per request over geography, user, channel, priority, weights and CDN health. The trade-off is a rule engine that needs its own testing and change history.
  • Filter, then sort. A filter engine removes ineligible CDNs, a sort engine orders the rest, and a rule-evaluation engine applies priorities. Rule storage, access and sync mechanisms keep the rules available to the playback service.
  • Always have an answer. If no rule matches or selection fails, the request falls back to stream options ordered by default weight. A priority-CDN override gives operators manual control, and fallback decisions are recorded.

Result. Playback for 10M+ active users, with buffering reduced from 1% to 0.07%.

  • Java
  • Spring Boot
  • MongoDB
  • SpEL rules

03 · Event ingestion at live-match scale

An event service that survives peaks and a Kafka outage

Problem. Playback events arrive in bursts during big live matches, about 80–90K per second. A spike or fault in one product should not take down the other, and events should not be lost if Kafka is unavailable.

  • Shorter request path. The service, rebuilt on Java 25, sends events straight to Kafka, with the extra queue in front of the producer removed and less logging on the request path. One pod went from about 400 to about 2,500 requests per second, roughly 6x.
  • Isolate the products. Xstream and IPTV each have their own event service, Kafka cluster and deployment, so a spike or fault stays inside one product and each scales independently.
  • Tier the topics. Critical events and routine watch events use different topics with different retention and replication.
  • Buffer when Kafka is down. Events are still accepted, held through Cloud Run and Pub/Sub, and replayed into Kafka by Kafka Connect on recovery. The trade-off, documented for the team: the buffered path cannot separate critical from routine events.

Result. About 6x per-pod throughput, peak load absorbed without cross-product impact, and no event loss during Kafka outages.

  • Java 25
  • Kafka
  • Kafka Connect
  • Pub/Sub
  • Cloud Run

04 · IPTV session service

One device at a time, without a single point of failure

Problem. IPTV needed to limit how many devices can watch at once, and to keep playback tied to the device that logged in, while traffic grew and a zone could fail.

  • Sessions tied to a device. A login creates a session. The token is opaque and bound to that device, and playback checks it while the user watches.
  • An atomic limit. The concurrent-device limit is configurable and enforced atomically, so two logins at the same moment cannot both succeed.
  • Multi-zone storage. Sessions live in multi-zone Aerospike, so the service keeps running if one zone has a problem. Login still works when the set-top-box details call fails.
  • Reusable validation. A shared client SDK lets the playback and SMS services validate tokens the same way, so there is one place to change the rules.

Result. IPTV login and device-level playback are handled by one service that scales with traffic and tolerates a zone failure.

  • Java 21
  • Spring Boot
  • Aerospike
  • SDK design

05 · Resilient Home and layout service

Keep the home screen open when something behind it breaks

Problem. The home and layout service depends on content sources and a CDN. If one is slow or down, the home page should still open, and a slow downstream call should not exhaust the service's threads.

  • Fallback with a kill switch. When the primary content fetch fails, the service retries against a fallback source. A kill switch turns that off, and a response header says when fallback content was served, so operators can see it.
  • CDN failover at the gateway. If the layout CDN fails, the gateway serves static layouts instead of an error. The trade-off is that static layouts are less personalized, which is acceptable for a degraded mode.
  • Protect the thread pool. Fixed thread-pool exhaustion under slow downstream calls, so a slow dependency cannot take down the whole service.
  • Faster generation. Personalized page generation went from 30 to 100 TPS, with about 30% lower latency, using Java 21, gRPC, thread-pool tuning and parallel asynchronous calls.

Result. Home and Rush stay available during dependency failures, and page generation scales to roughly 3x the previous throughput.

  • Spring Boot

How I work

Three habits the case studies share

  • Design for ordering

    Decide what must happen in order and enforce it structurally, for example by keying Kafka messages by user, instead of hoping races stay rare.

  • Isolate failure

    Give products, thread pools and storage zones their own boundaries so one fault stays small, and always keep a degraded path that still answers.

  • Measure before and after

    Pick the metric first (p99, throughput, buffering, recovery), take the baseline, and check it again after rollout.
