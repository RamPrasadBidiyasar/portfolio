01Ordering and data flow

Continue Watching and Watch Info v2

Per-user ordering for watch progress across devices, and a reactive read path for history, serving both the Xstream and IPTV apps.

Challenge
One user can write from several devices at the same moment, so writes needed a single order per user, and history reads had to stay fast at high volume.
My part
Redesigned it from scratch: watch events keyed by user ID go through Kafka into ScyllaDB. Re-architected reads on Spring WebFlux and reactive ScyllaDB, with independent loaders per section.

02Routing and decisions

Multi-CDN Routing

A rule engine that picks the right CDN for every IPTV playback request, with a guaranteed answer when no rule matches.

Challenge
Send each request to the best CDN as geography, load and CDN health change, and keep playback going when a CDN degrades.
My part
Built the routing engine: rules configured in MongoDB over geography, channel, priority, weights and CDN health, evaluated as filter, then sort, then pick, with a default-weight fallback.

03Throughput and recovery

Event Ingestion at Live-Match Scale

The service that takes in playback events from every client, rebuilt to absorb live-match peaks and survive a Kafka outage.

Challenge
Absorb 80–90K events a second at big matches, keep a spike in one product from hurting the other, and lose nothing while Kafka is unavailable.
My part
Rebuilt it on Java 25 with a shorter path straight to Kafka, separate Kafka clusters and stacks per product, and a Pub/Sub buffer that Kafka Connect replays on recovery.

04Concurrency and atomic limits

IPTV Session Service

Login and device-level playback for IPTV in one service, with a device limit that holds under concurrent logins.

Challenge
Enforce a concurrent-device limit that simultaneous logins cannot slip past, on storage that keeps working when a zone fails.
My part
Designed and built it on multi-zone Aerospike: adding a device is one atomic operation that returns the new count, with oldest-device eviction, device-bound tokens and one SDK shared by playback and subscription management.

05Fault isolation and fallback

Resilient Home

Keeping the home screen open when something behind it breaks, from a 5-minute outage to no error screens at 10–11x traffic.

Challenge
An Asia Cup match pushed layout-service latency to about 5 minutes. The home screen had to stay up at far higher traffic the next time.
My part
Bounded the queue, added an Envoy and Lua gateway filter that serves a prepared CDN page after 1.5 seconds or a 5xx, a fallback retry with a kill switch, and CPU boost with gradual pod warm-up.

04 · Case studies

Inside the systems, step by step.

Each case study covers the problem, the architecture, the request flow, the implementation, the trade-offs, failure handling and results. Here is how the first one works.

Request and event flow

Hover a step to find it in the diagram.

  1. The app sends a watch event to the sync API.
  2. The sync API publishes it to Kafka, keyed by user ID.
  3. Kafka keeps that user's events in order on one partition.
  4. A writer consumes the events in that order.
  5. It stores them in ScyllaDB, in separate Xstream and IPTV models.
  6. Reads go through a bucket-scoped cache over ScyllaDB.
  7. Watch Info v2 loads continue-watching, history and favourites in parallel.
  8. The client receives one response.
